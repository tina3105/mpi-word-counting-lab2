# Parallel Word Counting in a Text Corpus with MPI

## 2. Problem Description

Given a query of 200 words (`consulta.txt`) and a corpus of 3000 text files (`file_XXXX.txt`) generated by `generator.py`, count how many times each query word appears in the corpus and report the 10 most frequent ones.

Words are lowercased and split on whitespace, as in the sequential baseline. The generated corpus contains 44,951,458 tokens, and the query words appear 3,631,778 times in total.

## 3. Environment and Execution Instructions

### a. Experimental Plan

- **Dataset:** generated once with `generator.py` inside the Docker image `augustosalazar/slim-mpi:2`.
- **Process count:** p = 2, the value recommended by `detectar_procesos_mpi.py`. The script tested N = 1 to 4 and picked N = 2, with a median of 8.503 s.
- **Repetitions:** 3 runs for the sequential baseline, 3 runs for MPI version 1, and 3 runs for MPI version 2.
- **Metrics:**
  - Average total time `T_p`.
  - Speedup `S_p = T_seq / T_p`.
  - Efficiency `E_p = S_p / p`.
  - Load imbalance `LI = max(t_i) / mean(t_i)`, where `t_i` is the local processing time of process i.
- **Correctness check:** total tokens, total occurrences, and the top 10 must match the sequential output.

### b. Sequential baseline (`baseline_secuencial.py`)

The script reads `consulta.txt` into a lowercase set and then goes through every `file_*.txt` in `dataset/`. For each line it splits on whitespace, lowercases the tokens, adds them to the token count, and counts the ones that are in the query with a `Counter`. It writes `baseline_results.csv` and prints the top 10. The timer covers only the counting.

### c. MPI version 1 (`mpi1.py`)

1. Rank 0 reads `consulta.txt` and builds the set of query words.
2. Rank 0 lists the `file_*.txt` files in sorted order.
3. Rank 0 broadcasts the query words and the file list with `comm.bcast`.
4. Files are distributed statically in round-robin order: process `rank` takes `files[rank::size]`.
5. Each process counts the query words in its files and times this local step.
6. Results are gathered on rank 0 with `comm.gather`.
7. Rank 0 merges the partial counts, prints the number of files and the local time per process, computes LI, and prints the total time and the top 10.

### d. Test procedure

Commands used on Windows PowerShell with Docker Desktop, run from the repository folder:

```powershell
docker run --rm -v "${PWD}:/app" augustosalazar/slim-mpi:2 python /app/generator.py
docker run --rm -v "${PWD}:/app" augustosalazar/slim-mpi:2 python /app/baseline_secuencial.py
docker run --rm -v "${PWD}:/app" augustosalazar/slim-mpi:2 python /app/detectar_procesos_mpi.py
docker run --rm -v "${PWD}:/app" augustosalazar/slim-mpi:2 mpiexec --allow-run-as-root --use-hwthread-cpus --oversubscribe -n 2 python /app/mpi1.py
docker run --rm -v "${PWD}:/app" augustosalazar/slim-mpi:2 mpiexec --allow-run-as-root --use-hwthread-cpus --oversubscribe -n 2 python /app/mpi2.py
```

The dataset was generated once and reused for every run. Each run was executed one after another on the same machine.

Test machine: Intel Core i3-1005G1 @ 1.20 GHz (2 cores, 4 logical processors, virtualization enabled), 8 GB DDR4 RAM (7.8 GB usable), Windows host. Docker Desktop was allocated 4 CPUs and 3.717 GiB of memory (as reported by `docker info`).

## 4. Experimental Plan Execution

### a. Sequential baseline timing

| Run | Time (s) |
|---|---|
| 1 | 91.03 |
| 2 | 70.85 |
| 3 | 116.12 |
| **Mean (T_seq)** | **92.67** |

All three runs produced the same output: 44,951,458 tokens, 3,631,778 occurrences, and this top 10: a 785774, para 392156, sus 228913, otros 105530, ante 99832, unos 88794, otra 83901, vosotros 61617, mios 58420, tuya 56635.

### b. MPI version 1 timing results (p = 2)

| Run | Total time (s) | Process 0 local (s) | Process 1 local (s) | LI |
|---|---|---|---|---|
| 1 | 52.35 | 41.02 | 44.58 | 1.0416 |
| 2 | 50.75 | 36.32 | 43.86 | 1.0941 |
| 3 | 59.23 | 40.39 | 47.19 | 1.0777 |
| **Mean** | **54.11** | | | **1.071** |

Each process received 1500 files. Tokens and occurrences matched the baseline in every run, and so did the top 10.

**Speedup:** S_2 = 92.67 / 54.11 = 1.71. **Efficiency:** E_2 = 1.71 / 2 = 0.86.

### c. Load imbalance evidence

In all three runs, process 1 took longer than process 0, even though both had the same number of files. Its local time was 3.6 s, 7.5 s, and 6.8 s longer. The LI ranged from 1.04 to 1.09, so the slower process set the total time in every run.

### d. MPI version 2: correction and results (p = 2)

Version 2 (`mpi2.py`) changes only the distribution step. Rank 0 reads each file's size, sorts the files from largest to smallest, and assigns each file to the process with the smallest accumulated size so far (a greedy longest-processing-time assignment). Each process receives its list with `comm.scatter`, and the rest of the program matches version 1. The file count per process went from 1500/1500 to 1499/1501.

| Run | Total time (s) | Process 0 local (s) | Process 1 local (s) | LI |
|---|---|---|---|---|
| 1 | 68.72 | 44.08 | 55.90 | 1.1182 |
| 2 | 58.52 | 32.47 | 35.56 | 1.0454 |
| 3 | 71.80 | 51.94 | 54.12 | 1.0206 |
| **Mean** | **66.35** | | | **1.061** |

Tokens, occurrences, and the top 10 matched the baseline in every run.

**Speedup:** S_2 = 92.67 / 66.35 = 1.40. **Efficiency:** E_2 = 1.40 / 2 = 0.70.

## 5. Analysis

### a. Parallel performance

Version 1 improved on the sequential baseline. Its average time was 54.11 s against 92.67 s, which gives a speedup of 1.71 against an ideal of 2 (85.6% of ideal, efficiency 0.86). The gap likely comes from three sources:

- **Shared resources:** both processes read files from the same disk and run inside the same Docker container, so reads do not scale perfectly.
- **Imbalance:** process 1 was consistently slower, so the total time is set by the slower process.
- **Measurement noise:** the sequential runs ranged from 70.85 s to 116.12 s, so the baseline mean is itself uncertain.

These causes are inferred from the measurements. They were not tested separately.

### b. Load balance

Version 1 showed a small but consistent imbalance. Process 1 was slower in all three runs, with LI between 1.04 and 1.09 (mean 1.07). The per-file work is the same for both processes, so the cause is probably not the data assigned to each process.

Version 2 did not reduce the imbalance enough to improve performance. Its LI was 1.02 to 1.12 (mean 1.06), almost the same as version 1. Its average time was higher, 66.35 s against 54.11 s. Process 1 was again slower in all three runs, even though the files were distributed by size. This suggests that file size does not predict processing time well here, and that the imbalance comes from something else, for example how the two processes are placed on the CPU.

### c. Limitations

- **Few runs:** three runs per configuration, with a spread of about 20 s between runs. The 12 s difference in average time between versions is at the edge of that noise, so the ranking of versions 1 and 2 is suggestive but not conclusive.
- **Single machine and environment:** all runs were on one Windows host with Docker Desktop, which adds a virtualization layer. The host has 2 physical cores with hyperthreading, so the two MPI processes may share a physical core. The host's 8 GB of RAM was almost fully used during the runs (about 245 MB available in one reading), and Docker was limited to 3.717 GiB, which can add paging and timing noise.
- **Single process count:** only p = 2 was tested, as required. The calibration script's own measurements for N = 2 and N = 4 differed by only 0.27 s, which is within noise, so p = 2 is a weak optimum.
- **Uncontrolled background load:** other processes on the host were not stopped during the runs.
- **Timing scope:** the sequential timer covers only the counting, and the MPI timer starts after the barrier and ends after the gather. Neither includes container startup or `mpiexec` launch, so the two timing windows are similar but not identical.

These limitations weaken the speedup and efficiency values in particular. The correctness results are not affected, since tokens, occurrences, and the top 10 matched in all nine MPI runs.

## 6. Conclusions

For this problem I would recommend the static round-robin distribution of version 1. It was faster on average (54.11 s against 66.35 s), had higher speedup (1.71 against 1.40), and had higher efficiency (0.86 against 0.70). Its load imbalance was essentially the same as version 2's (LI 1.07 against 1.06). Distributing files by size balanced the file counts but did not balance the work, because process 1 remained slower in every run. The next useful step would be to investigate process placement and I/O contention before trying another distribution strategy.
